# M4 深度内容脱水

**什么情况下读我**：内容本身扎实——优质长文、技术博客、书籍章节、长科普视频、播客、会议录音转写。作者没有明显利益诉求，目标是**压缩体量、保留骨架**，让读者用最短时间拿到真正有用的东西。会议转写这类私有记录同样适用：只压缩、不强行祛魅，不硬挑刺。

> 如果内容在讲“某个产品多好”，大概率是 M2；如果在讲“某事件的各方说法”，大概率是 M5。M4 的特征是：**作者在认真论证一件事**。

## 一、三步做法

### 1. 还原论证结构

先别急着压缩，先搞清楚作者在论证什么：

```text
核心主张 → 主要论据（2–4 条） → 结论
```

- 核心主张：作者想让你相信什么？一句话说清。
- 主要论据：支持主张的关键证据、数据、案例、推理。
- 结论：作者最终要你带走什么。

### 2. 压缩

可以压缩的：铺垫、背景重复、故事性的开场、反复强调、过渡句、作者的自我介绍。
**不可以压缩的**：关键数字、限定条件、反例、作者的保留与不确定。

### 3. 保留限定条件

这是 M4 最容易出问题的地方。

| 反例（过度压缩） | 正例（保留限定） |
| :--- | :--- |
| “作者认为早起一定能提高效率。” | “作者认为，对大多数上班族，固定作息比早起本身更重要；他的结论建立在对 200 名志愿者的两周记录上。” |
| “这个算法比旧算法快。” | “在数据量超过 100 万条时，新算法比旧算法快约 30%；数据量小时差别不明显。” |

“有条件成立”不能被压缩成“一定成立”。作者写了反例或例外，就留下。

## 二、长内容怎么处理

- 内容很长（长文、长字幕）时，**分段提炼**：每段先写一两句，再汇总；
- 在报告开头写：“内容较长，已分段处理。”
- **不能只读开头就下结论。** 如果你没读完，就明说读到哪里。

## 三、视频与播客

- 逐字稿带时间戳时，关键观点标注时间点，如 `[01:24]`；
- 说明内容来源（字幕 / 语音转文字 / 画面），并提醒“语音转文字可能有错字，人名和数字以原视频为准”；
- 口语里的“嗯”“就是说”“你知道吗”直接去掉，但不要去掉作者的转折和保留。

## 四、输出组织（统一遵循 `SKILL.md` 第 9 步输出手册）

不论长短，都要留住五个实质要素：**核心主张、主要论据（带限定条件与反例）、作者的保留或代价、读完能带走的实用做法、值不值得读原文**。

- **同一判断与数字只说一次**，不要让开头结论、论证骨架、核查三遍重复报同一组数字；
- **干净短手记 / 短分享**：用 2–3 个自然段直答即可，不硬套 `## 论证骨架` 固定子块，也不在末尾硬贴综合评级标签；
- **长文章 / 深度博客 / 长视频转写**：可用精简 `##` 小节方便扫读，把事实与论证合在一节讲完，不另留重复栏。

## 五、M4 里仍然要做的事

- **校准**：M4 不等于“不用检查”。如果作者引用了关键数字，核查最关键的几条；有明显错误要指出；
- **不尬黑**：好文章就说好，不为显得有判断力硬找缺点；
- **指出作者没有论证的跳跃**：只在确实存在时写，并给出具体位置；
- **利益**：如果作者是某产品的创始人、文章在为自己的产品背书，要在开头说明并考虑加辅模式 M2。

## 六、长材料示例（虚构；示范长文如何使用精简 `##` 小节）

**材料**：技术博客《为什么我们把数据库从单机迁到了集群》（作者为虚构公司“墨石科技”的后端工程师），约 4000 字。文章讲述：单机在访问量增加后出现延迟；他们对比了 3 种方案；选择了方案 B；迁移后延迟从平均 800ms 降到 200ms；也提到迁移花了 3 个月、成本增加约 40%、需要额外维护团队。

```markdown
## 一句话讲人话
墨石科技这篇长文讲的是：单机数据库顶不住高并发时，迁到集群能显著降延迟，但换来的是三个月工期、更高成本和额外运维，小流量团队别跟风。

## 论证骨架与限定条件
- **核心主张与论据**：高峰期单机平均延迟升至约 800ms 且无法继续靠升配解决；团队横向对比三种方案后选了改造成本和风险最低的方案 B，迁移完成后平均延迟降到约 200ms。
- **作者主动交代的代价与保留**：迁移耗时 3 个月、整体成本涨约 40%，且必须配专门运维人力；作者明确提醒“访问量不大时不建议这么干”。
- **带走什么 / 值不值得读原文**：迁之前先确认瓶颈真在数据库，评估时把运维人力算进去。正在做数据库选型、想看三套方案对比表和迁移步骤的人值得读原文；只想知道结论看这里就够。

## 核查与建议
以上性能与成本数字来自作者自述，未查外部资料（技术实践复盘里自报内部指标很常见，不算缺陷）；文章自洽且主动交代了代价与适用边界，文本本身可信度高。做后端架构选型时可作参考，非技术岗位不用管。
```

**这个示例体现的校准点**：长文用 3 个精简 `##` 小节方便扫读；每组数字（800ms、200ms、3 个月、40%）全篇只出现一次；没有给一篇扎实文章硬挑刺，保留了作者自己写的代价与限定。
