## 原版在哪一步不能继续

| 入口或步骤 | 原版要求 | 这次能做什么 |
|---|---|---|
| 第 1–3 步：原文与主张 | 可接受粘贴文本，不强制 `fetch-content`。正式运行要求取源前记实际时间并缓存规范化原文；通读，按位置穷举、分类、拆分主张，再分承重与附带。 | 四题均可读，可定位主张。下表只列用于判断可运行性的例子，不冒称已交付穷举清单。本次只准写本文件，未建立正式原文缓存。 |
| 第 4 步：独立核查 | 对实际核查的事实主张，规则是 “One claim, one search”：检索独立来源、按文档分层、将转引折叠回原始出处；承重主张不设条数上限，首查不足可换角度再查至多三次。给出误导或虚假判断前先检验宽厚读法。 | **首个实质阻塞：**四题都含事实主张，均不能发起首次独立检索。`unverifiable (searched)` 表示确实搜过；`by construction` 只适用本质上不可从外部核实的具体主张；`not checked` 是预算边界。不能用其中任何一个标签把整轮禁搜改写成一次完成的核查。 |
| `claims-only` | 仅用户明确要主张文件时启用。它不是只做提取，而是完整执行到第 4 步，写 `.claims.jsonl` 与标记模式的 `.run.json`，用 `tally.py --claims` 携 `--source` 核验每条记录及引文，直至退出 0。无 shell 不能运行此模式，须回到 full。 | 不跳搜索，也不跳脚本；即使成功，该模式也没有报告或 BS 分数。手工列几条主张不是该模式的输出。 |
| `full` / `quick` | 默认 full。quick 须用户明确求快，只减少附带主张（最多五条）、省略 `coverage-check` 和敌意读者段，不减已查主张的核查深度。报告需做炒作信号扫描、写结论与运行记录；常规路径用 `tally.py --compose` 生成表格，再用 `tally.py --fix` 携 `--source` 验收到退出 0。查询和不可达来源在运行中记录。 | **第二个独立阻塞：**即使另行提供证据，本轮也不许运行上游 `tally.py`。无 shell 时可手排报告表格，不是免除最终验收；不能以手算 tally、手拟报告或 BS 分替代。 |

其他条件不构成离线模式：`coverage-check` 只在来源广度无法从手头结果判断时有条件使用；若证据引用 DOI，则须运行撤稿检查；`report-card` 未安装可跳过 HTML 渲染，但 Markdown 验收不随之消失。审本人草稿的特例只跳第 1–2 步，仍需抽取和核查。

## 怎样才算公平复测

若目标仍是这四题、这套封闭证据，应保留“协议不适用／未评分”，不能推论哪个系统更好。若要测原版最近邻，另开一轮：换成有可追溯现实来源、允许检索的材料（尤其不能暗中改写 Q09），同一模型、相同输入、检索权限、时间与工具预算运行各臂；记录模型配置、查询、不可达来源、逐题耗时及脚本退出码。预先允许隔离运行固定版上游、提供 `uv` 和可写目录，保留原文缓存、主张、运行记录及通过门槛的产物；可选的 HTML 不影响验收。原文给出的成本例是 19 条可核查主张约 25–30 次搜索，**不是本四题的成本实测**。给所有臂同一份证据包也可另测离线阅读，但必须标为改编协议，不能据此补报原版成绩。
